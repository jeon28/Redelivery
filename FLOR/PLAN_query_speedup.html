FLOR 반납조회 속도 개선 계획

2026-11-06 · 대상: scraper/scrapers/flor.py (Phase 1) · routers/query.py + 프론트 2개 폼 (Phase 2)

1. 목표

  • Phase 1 (즉시 적용): 사이트 동작은 그대로 두고, 코드에 박힌 고정 대기와 헛도는 단계를 없앤다. 신규 발급 1건 기준 35초 → 15~18초.
  • Phase 2 (별도 적용, 협의 후): 다중조회에만 "Apply 우선" 흐름을 적용해 컨테이너 수에 비례해 늘어나는 Status 탭 검색 횟수를 줄인다. 단건 통합조회는 현행 "Status 우선"을 유지한다.
  • FLOR 외 임대사, 로그인·세션 재사용, 슬라이더 캡차, Confirm 안전장치(disabled 체크, precleared 제외)는 변경하지 않는다.

3. Phase 1 — 고정 대기 제거 + 헛도는 단계 제거 즉시

원칙: asyncio.sleep(N)을 "다음 단계가 필요로 하는 DOM 상태"를 기다리는 조건 대기로 바꾼다. 각 조건 대기에는 기존 sleep보다 긴 상한(timeout)을 두고, 상한 초과 시 예외 대신 로그만 남기고 진행한다(현행 동작과 동일한 안전망).

3-2. Step3 4초 타임아웃 제거

현재: "Redelivery number:" 문구를 최대 4초 기다리고, precleared가 없는 보통 케이스는 매번 4초를 다 쓴다.
변경: Step3 테이블 행 수를 300ms 간격으로 2회 연속 비교해 안정되면 즉시 파싱(상한 4초 유지). precleared 문구는 파싱 시점에 한 번만 확인. Unit Detail 영역이 늦게 그려지는 케이스는 행 수 안정화 조건이 흡수한다.

3-3. Confirm 후 Status 탭 재조회 삭제

현재: Confirm 화면에서 번호를 못 읽으면 Status 탭으로 이동해 재검색(6.6s). 로그상 항상 실패하고 결과 문구는 "반납번호 미확인 — Florens Status 탭 확인 필요".
변경: 재조회를 하지 않고 바로 결과를 돌려준다. 문구는 두 가지로 구분한다.

  • Confirm 클릭 성공 + 번호 미표시 → "발급 요청 완료 — 반납번호는 잠시 후 [Status 조회] 버튼으로 확인" (available=True, booking_ref 없음)
  • Confirm 버튼 없음/disabled/클릭 실패 → 현행대로 "반납번호 미확인 — Florens Status 탭 확인 필요"

기존 결과표의 Status 조회 버튼(/status-detail, 11초)이 번호 확인 경로로 그대로 쓰인다. _backfill_ppr_from_status 함수는 삭제하지 않고 호출만 제거(향후 옵션으로 복구 가능).

3-4. Step3 파싱 범위 한정 (정확성)

  • _parse_step3의 document.querySelectorAll('table') → 화면에 보이는 행만(tr.offsetParent !== null) 수집. 비활성 탭 패널(display:none)에 남은 Status 탭 상세표가 제외된다.
  • Status 탭에서 +More로 펼친 행은 추출 후 다시 접는다(같은 아이콘 재클릭, 실패해도 무시).
  • Step3 행 덤프 로그를 행당 300자로 잘라 logging 예외를 막는다.

4. Phase 2 — 조회 모드별 흐름 분리 별도 적용 · 협의 후

4-1. 분리 적용 가능 여부: 가능

화면호출현재 구분 수단
단건 통합조회 (SingleLookupForm.tsx)POST /api/query → POST /query, containers: [1개]없음 (같은 엔드포인트, 같은 body)
다중조회 (SearchForm.tsx)동일, containers: [n개]

백엔드 QueryRequest에 선택 필드 flow: "status_first" | "apply_first"(기본값 status_first = 현행)를 추가하면 두 화면을 독립적으로 제어할 수 있다. 컨테이너 개수로 추론하지 않고 프론트가 명시하게 해, 다중조회 화면에서 1건만 넣은 경우에도 선택한 흐름이 적용되게 한다. 다른 임대사 스크래퍼는 이 필드를 무시한다.

4-4. 리스크

  • Status 우선으로 바꿨던 이유(Step3 파싱 불안정: fixed column으로 행 분리, Unit Detail 지연 렌더)가 재현될 수 있다. 당시 패치(bidirectional sweep, wait_for_function)는 현재 코드에 일부만 남아 있어 Phase 2 착수 시 Step3 파싱을 다건 케이스로 재검증해야 한다.
  • 반대로 11-03 로그에서는 Status 탭이 "결과 없음"인데 Step3는 precleared PPT02419를 정확히 잡았다. 두 소스가 서로 보완 관계이므로 다중조회에서 Status 보강 실패 시 Step3 번호를 그대로 쓰는 폴백을 둔다.
  • 프론트 "FLOR 6개 이상 입력" 경고문은 Phase 2 적용 후 문구 조정.

Phase 2는 Phase 1 배포 후 실측을 보고 착수 여부를 결정한다. 착수 시 별도 계획서 없이 본 문서 4장을 기준으로 진행.

6. 검증 (Phase 1)

  1. 로컬 python -c "import scrapers.flor" 임포트 검증.
  2. Cloud Run 배포 (사용자 승인 후 gcloud run deploy).
  3. 이미 발급된 컨테이너 1건 조회 → Status 경로로 번호·유효기간 표시, 소요 10초 이내 확인.
  4. 신규 컨테이너 1건 조회 → Apply → Confirm → "발급 요청 완료" 문구, 소요 20초 이내 확인. 수 분 후 [Status 조회] 버튼으로 번호 확인.
  5. 신규 3건 이상 조회 → Step3 valid 수가 입력 수와 일치하는지(1498 같은 비정상 값 없음) 로그 확인.
  6. 로그에서 각 조건 대기의 timeout 경고가 반복되는 지점이 있으면 상한 조정.
